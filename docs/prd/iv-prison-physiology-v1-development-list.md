# 司法监管生理监测 V1 开发列表

状态：建议拆分
来源：`docs/prd/iv-prison-physiology-v1-prd.md`
上游底座：`docs/prd/supervision-event-closure-v1-prd.md`、`docs/prd/supervision-event-closure-v1-development-list.md`
拆分原则：优先 V1-P0 红色生理急症闭环；每个开发项尽量形成可独立演示、可测试的竖切片。生理专项不重复实现监管事件、处置任务、关闭校验和职责隔离，而是复用监管事件处置闭环 V1。

## 总体顺序

1. 先完成监管事件处置闭环 V1 的 P0：事件中心、告警转事件、处置任务、复核、关闭校验、证据链、职责隔离。
2. 再跑通一个高危生理点位、一类上游生理输入、一条红色急症闭环。
3. 再补齐身份降级、低可信保护、人工替代、超时升级、误报沉淀和行为生理融合。
4. 最后进入 P1 治理入口和 P2 辅助运营预留。

## V1-P0 开发切片

### 1. 确认生理专项接入监管事件闭环的数据边界

类型：HITL
Blocked by：无
User stories covered：30

要交付：

- 确认生理红色急症如何接入监管事件处置闭环 V1。
- 确认 `Physiology Sample`、可信 `person_id`、红色规则和质量标签如何作为监管事件证据来源。
- 确认 VIDEO、DEVICE/iot-sink、WEB、iot-system 之间的生理样本、身份、动作、证据契约。
- 输出生理专项的数据迁移、接口契约和权限接入口径。

验收标准：

- 有明确监管事件闭环复用边界。
- 有 `Physiology Sample -> Supervision Event` 输入边界说明。
- 有生理 P0 必需对象清单：样本、点位、身份、动作、复测、证据、readiness、报表。

### 2. 生理点位台账与 readiness 基线

类型：AFK
Blocked by：1
User stories covered：17, 18

要交付：

- 支持配置一个高危生理点位。
- 记录设备/SDK 来源、点位、标定状态、在线状态、隐私策略、分析时段和 SLA。
- 提供 readiness 基线检查入口，至少能显示 `ready`、`manual_required`、`blocked_by_customer`、`simulated`、`skipped_not_ready`。

验收标准：

- 可以创建、查看、编辑一个高危点位。
- 点位缺少标定或依赖时，readiness 能显示不 ready 原因。
- 页面和接口都有基础权限控制和审计记录。

### 3. 上游生理输入归一化为 Physiology Sample

类型：AFK
Blocked by：2
User stories covered：15, 16, 25

要交付：

- 提供上游红外、近红外、热成像设备或厂商 SDK 输出的样本接入契约。
- 归一化为 `Physiology Sample`：来源、点位、时间窗、指标、质量标签、置信度、模型或设备版本。
- 提供样本查看和调试入口。

验收标准：

- 可注入一条样本并在系统内查询。
- 样本包含呼吸、心率、温度、质量标签、置信度和版本信息。
- 无效样本返回可解释错误，不生成个人事件。

### 4. 可信 person_id 绑定与身份不可信降级

类型：AFK
Blocked by：3
User stories covered：13, 14, 15

要交付：

- 将人脸匹配、床位绑定、点位绑定、`correlation_id` 等作为身份候选。
- 接入或模拟监管台账/业务确认后的可信 `person_id`。
- 无可信 `person_id` 时进入匿名质量统计或人工复核队列。

验收标准：

- 只有身份候选时不生成个人生理事件。
- 可信 `person_id` 存在且质量合格时允许进入事件创建流程。
- 身份候选证据保留在可审计记录中。

### 5. 低可信窗口保护与匿名质量统计

类型：AFK
Blocked by：3
User stories covered：15, 16, 29

要交付：

- 识别 ROI 丢失、遮挡、强运动、热源干扰、厚被遮挡、设备未标定、有效采样不足等低可信原因。
- 低可信窗口进入匿名质量统计或点位整改，不进入个人事件和个人基线。
- 提供低可信原因查询和统计入口。

验收标准：

- 低可信样本不创建个人事件。
- 低可信样本不写入个人基线。
- 低可信原因可被审计和报表统计。

### 6. 红色生理急症创建统一 Event

类型：AFK
Blocked by：4, 5
User stories covered：4, 13, 21, 30

要交付：

- 当样本质量合格、可信 `person_id` 存在且命中红色急症规则时，创建个人生理事件。
- 事件进入统一事件中心，状态从 `candidate` 或 `created` 开始流转。
- `Alert`、样本、身份和规则命中记录作为事件证据来源。

验收标准：

- 红色生理急症不只停留在告警列表。
- 事件详情能看到样本、身份、规则和初始证据。
- 事件状态变化有日志和审计。

### 7. 事件中心列表、详情和状态时间线

类型：AFK
Blocked by：6
User stories covered：4, 10, 30

要交付：

- 事件中心支持查看红色生理事件。
- 事件详情显示状态、责任链、样本、证据、动作、复测、readiness 和审计摘要。
- 状态时间线可追踪创建、派发、接收、处置、复测、关闭校验和关闭。

验收标准：

- 指挥中心值班员能从事件列表进入事件详情。
- 审计人员能复盘事件生命周期。
- 事件详情不混用告警字段表达事件关闭语义。

### 8. 医务、干警、领导动作队列与人工替代闭环

类型：AFK
Blocked by：6
User stories covered：1, 2, 3, 5, 8, 9, 18, 19, 20

要交付：

- 红色事件创建后生成医务动作、监区干警动作和值班领导关注动作。
- 动作状态支持 `pending`、`sent`、`acknowledged`、`real_success`、`manual_completed`、`manual_signed`、`timeout`、`blocked_by_customer`、`skipped_not_ready`、`simulated`。
- readiness 不具备时走人工替代闭环。

验收标准：

- 动作状态独立于事件状态。
- 通知发送成功不等于医务复测完成。
- 人工替代可完成业务处理，但不计入真实接口成功。

### 9. 医务复测任务和复测回填

类型：AFK
Blocked by：8
User stories covered：6, 7, 8, 23

要交付：

- 为红色生理事件生成医务复测任务。
- 医务人员可回填复测指标、医学判断、真异常/误报、误差原因、SOP 结果和附件。
- 无法复测时可提交原因并进入审批。

验收标准：

- 复测记录与事件、样本、动作关联。
- 误报事件不删除原事件和证据。
- 无法复测原因需要审批后才能进入关闭校验。

### 10. 关闭校验与证据链拦截

类型：AFK
Blocked by：7, 8, 9
User stories covered：2, 7, 10, 11

要交付：

- 实现红色事件关闭校验。
- 校验动作状态、医务复测或无法复测审批、现场处置、证据链、责任链、readiness 和关闭权限。
- 缺关键材料时进入 `rework_required` 或等价补充状态。

验收标准：

- 缺复测、缺动作、缺证据或缺责任链时不能普通关闭。
- 证据链缺口不阻塞急症派发，但阻塞普通关闭。
- 关闭、驳回、补充材料均进入审计。

### 11. 医务和干警超时升级

类型：AFK
Blocked by：8, 9
User stories covered：3, 5, 9

要交付：

- 配置医务接收、复测回填、干警到场等超时阈值。
- 超时后动作进入 `timeout`，并升级到监区值班长、指挥中心或带班领导。
- 事件详情和报表显示超时升级记录。

验收标准：

- 超时有动作状态、催办记录和升级记录。
- 超时事件不能绕过复测或审批直接关闭。
- 升级链路可审计。

### 12. 行为事件与生理事件融合关系

类型：AFK
Blocked by：6, 7
User stories covered：21, 22

要交付：

- 支持同一帧、同一轨迹、同一点位、同一身份或时间窗口的行为与生理关联。
- 行为事件和红色生理事件同时触发时，两类事件都保留。
- 融合成功或冲突时记录关系和原因。

验收标准：

- 倒地和红色生理急症同时出现时，生理急症不被行为事件覆盖。
- 事件详情可查看融合关系或冲突原因。
- 生理急症仍触发医务动作。

### 13. P0 报表和统计口径

类型：AFK
Blocked by：8, 9, 10, 11, 12
User stories covered：18, 19, 20, 28, 29

要交付：

- 报表区分红色事件总数、已关闭、待复测、超时升级、真实接口成功、人工完成、人工签字、模拟、客户阻断、未 ready 跳过、真异常、误报、无法复测、身份降级和低质量降级。
- 成功率拆分为真实接口成功率、人工闭环完成率、复测完成率和关闭校验通过率。

验收标准：

- 报表不只输出一个“成功率”。
- 人工替代、模拟、客户阻断、未 ready 不计入真实接口成功。
- 报表能支撑 P0 验收脚本 A-H 的结果复盘。

### 14. 敏感证据权限、导出审批和审计

类型：AFK
Blocked by：7, 10
User stories covered：10, 11, 12, 27

要交付：

- 增加生理证据查看、医务复测、治理写入、事件关闭、导出审批等权限。
- 敏感证据导出需要审批和审计。
- 心理辅助或健康画像相关预留输出带 `not_standalone_determination` 标识。

验收标准：

- 非授权角色不能查看医务判断和敏感生理证据。
- 导出有审批、导出记录和审计记录。
- 心理辅助预留不作为 P0 判定依据。

### 15. P0 验收脚本和演练数据

类型：AFK
Blocked by：10, 11, 12, 13, 14
User stories covered：1-30

要交付：

- 准备验收脚本 A-H 的测试数据、操作步骤和预期结果。
- 覆盖正常闭环、身份不可信、低质量窗口、人工替代、医务超时、误报、客户未 ready、行为生理同时触发。
- 输出演练记录模板。

验收标准：

- 八条脚本均可执行并留痕。
- 每条脚本都有通过条件和不通过条件。
- 演练结果能映射到证据链和报表。

## V1-P1 治理开发切片

### 16. 最小治理入口

类型：AFK
Blocked by：9, 13
User stories covered：23, 24, 25, 26

要交付：

- 接收复测结论、误差原因、低可信原因、样本证据、模型或设备版本材料。
- 支持把误报、低质、无法复测、接口失败、超时升级沉淀为治理样本。

验收标准：

- 误报和低可信原因可从事件闭环进入治理入口。
- 治理样本具备来源、版本、原因和审计记录。
- 治理入口不阻塞 P0 急症闭环。

### 17. 生理模型治理预留

类型：AFK
Blocked by：16
User stories covered：25, 26

要交付：

- 为生理模型版本、设备版本、参数版本、上线状态预留治理字段和页面入口。
- 预留影子模式、灰度、冠军-挑战者、回滚的记录结构。

验收标准：

- 每个样本可追溯模型或设备版本。
- 新版本评估材料可进入治理入口。
- 模型治理预留不影响红色急症主通道安全。

## V1-P2 辅助运营开发切片

### 18. 群体趋势、健康画像和心理辅助预留

类型：HITL
Blocked by：14, 16
User stories covered：26, 27

要交付：

- 预留单所群体趋势、本地健康画像、心理辅助复核的菜单、权限、审计和数据边界。
- 所有心理辅助或画像输出默认带 `not_standalone_determination`。
- 明确这些能力不反向阻塞 P0 急症闭环。

验收标准：

- P2 入口有权限和审计边界。
- 心理辅助输出不能作为惩戒、医学诊断或监管最终判断。
- P2 预留不改变 P0 事件关闭条件。

## 推荐首轮迭代

第一轮建议只做 1-10：

1. 事件中心归属与数据边界。
2. 生理点位台账与 readiness 基线。
3. 上游生理输入归一化。
4. 可信身份绑定与身份不可信降级。
5. 低可信窗口保护。
6. 红色生理急症创建统一 Event。
7. 事件中心列表、详情和状态时间线。
8. 医务、干警、领导动作队列与人工替代闭环。
9. 医务复测任务和复测回填。
10. 关闭校验与证据链拦截。

第一轮完成后，应能演示脚本 A、B、C、D 的核心路径，再进入超时升级、融合、报表、权限导出和完整验收脚本。
