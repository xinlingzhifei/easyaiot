# IV 生理监测 V1 需求梳理草案

状态：领域口径、事件模型、可信身份来源、医务通道、生理 worker 来源和 V1-P1/P2 交付深度已确认  
来源文档：`E:\yFeiVideo\docs\IV系统_系统功能说明书_生理监测全量V1融合版.md`

## 1. 已确认口径

已确认：该需求是“司法监管行业方案里的生理监测闭环”，不是通用 AIoT 健康监测能力。

本文件仍是需求梳理草案；已确认的领域词汇同步固化到根级 `CONTEXT.md`，关键边界决策同步记录到 `docs/adr/`。

## 2. 一句话边界

yFeiEye 当前具备设备接入、视频流、算法任务、告警、通知、图片/录像证据、权限和审计底座；说明书要求在这些能力之上补齐“可信身份绑定 - 生理采样 - 生理事件 - 行为与生理融合 - 急症触达 - 医务复测 - 证据链 - readiness - 治理与验收”的完整闭环。

这不是给现有告警列表增加心率、呼吸率字段。

## 3. 说明书强约束

V1 必须同时覆盖视频行为识别闭环和全量生理监测闭环。

V1 不再只验收红外点位台账和匿名质量统计，而是必须形成以下闭环：

1. 生理事件
2. 健康/急症通道
3. 医务复测
4. 证据链
5. 数据治理
6. 模型治理
7. 演练验证
8. 审计报表

合规底线：

1. 无可信 `person_id` 不生成个人生理事件。
2. ROI 丢失、严重遮挡、强运动伪影、设备未标定或环境干扰严重时，不生成个人生理事件。
3. 低可信窗口只能进入匿名质量统计、点位质量分析或人工复核队列。
4. 心理辅助必须标记 `not_standalone_determination`，不得单独用于惩戒、监管定性或医学判断。
5. 模拟、人工签字、客户阻断不得折算为真实接口成功。
6. 红色生理急症不能被普通行为事件吞掉。

## 4. yFeiEye 现有承载点

### 4.1 可以复用的能力

设备与视频：

- 摄像头、NVR、GB28181、ONVIF 接入。
- 点位、地图分布、设备在线状态、流转发、录像回放。
- 多路实时分析和抓拍分析。

算法与模型：

- 算法任务管理。
- 实时任务和抓拍任务。
- 模型训练、部署、导出和推理服务。
- 区域绘制、布防时段、告警抑制。

告警与通知：

- `VIDEO.models.Alert` 已承载算法告警记录。
- `iot-sink` 已消费告警 Kafka 消息并落库。
- 已有图片上传 MinIO、录像路径、通知配置、通知状态。
- 已有人脸库、车牌库和同帧 `correlation_id`。

系统底座：

- 用户、角色、菜单权限。
- 操作日志、登录日志。
- 短信、邮件、站内信、Webhook 等通知通道。

### 4.2 不能直接复用为完成态的能力

现有 `Alert` 不是说明书里的完整“事件中心”：

- 缺少事件状态机。
- 缺少动作队列。
- 缺少责任链。
- 缺少医务复测任务和复测记录。
- 缺少关闭校验。
- 缺少 readiness 状态。
- 缺少生理证据链。

现有 `task_type` 只表达 `realtime` / `snap`，不能表达 `behavior` / `physiology` / `fusion`。

现有图片路径和录像路径不是完整证据链，只能作为证据链的一类材料。

现有 `phsyicalModal` 是 IoT 物模型，不是生理监测领域模型。

## 5. 目标能力分层

### 5.1 V1-P0 必须先跑通

设备与点位：

- 红外、近红外、热成像和可见光 rPPG 点位台账。
- 点位距离、角度、隐私策略、分析时段。
- 设备标定、在线状态和点位 SLA。

生理采样：

- ROI 类型：鼻口、前额、颈部、胸腹、被面起伏。
- 质量信息：遮挡、运动伪影、热源干扰、设备未标定、有效采样占比。
- 指标窗口：呼吸频率、呼吸幅度、心率、体表温度、无呼吸时长、信号质量。
- 模型版本和证据引用。

身份与降级：

- 个人生理事件必须绑定可信 `person_id`。
- 绑定失败进入匿名质量统计或人工复核。
- 低可信窗口不写入个人基线。

事件与融合：

- 行为事件、生理事件、融合事件都必须能被事件中心承载。
- 同一帧倒地和生理急症同时出现时，两类事件都发布。
- 融合冲突时保留原事件，新增冲突原因和复核入口。

急症与医务：

- 红色生理急症直达医务，同时同步监区干警和值班领导。
- 医务动作必须有状态、回执、超时升级。
- 医务复测必须回填体征复测、医学判断、是否真异常、误差原因、SOP 执行结果和附件。
- 红色急症未复测或未审批不得直接关闭。

证据与审计：

- 生理指标快照。
- ROI 可信度。
- 基线对比。
- 行为片段。
- 判定依据。
- 处置动作。
- 医务记录。
- 审计记录。
- 导出审批。

readiness：

- 真实医务适配器、医务账号、班次、回执、复测回填、超时升级要明确。
- 不具备真实接口时进入人工替代闭环，并保留状态。
- `ready`、`degraded`、`manual_required`、`manual_signed`、`blocked_by_customer`、`simulated` 不能混算。

### 5.2 V1-P1 建议实现或预留

- 生理数据治理。
- 复测结论回流。
- 误差原因沉淀。
- ROI 失败原因沉淀。
- 匿名质量统计。
- 难例池。
- 波形精标基础入口。
- 生理模型版本治理。
- 影子模式、灰度发布、冠军-挑战者和回滚。
- 红队演练与失败模式库。

### 5.3 V1-P2 辅助运营

- 心理辅助复核。

V1-P2 不能反向阻塞 V1-P0 急症闭环，但心理辅助合规标识必须从一开始纳入设计。

## 6. 建议领域对象

以下对象用于梳理需求边界，不代表最终表名或代码结构。

### 6.1 Event

统一业务事件。用于承载行为事件、生理事件、融合事件和人工事件。

关键含义：

- 有业务等级。
- 有状态流转。
- 有责任链。
- 有动作队列。
- 有证据链。
- 有关闭条件。

建议不要把它等同于现有 `Alert`。

### 6.2 Alert

算法告警记录。它是事件输入或事件证据来源之一。

当前 yFeiEye 里的 `Alert` 更接近这个含义。

### 6.3 Physiology Sample

生理指标样本或指标窗口。记录 ROI、质量、指标、模型版本和采样上下文。

它不必然生成个人生理事件。

### 6.4 Physiology Event

可信身份和质量条件满足后生成的个人生理事件。

必须具备可信 `person_id` 或业务确认绑定。

### 6.5 Anonymous Quality Window

无法绑定身份或低可信的生理窗口。用于点位质量、设备整改和匿名统计，不进入个人事件和个人基线。

### 6.6 Fusion Event Link

行为事件、生理事件、同帧目标、轨迹、点位或身份之间的关联关系。

它应解释为什么融合、为什么冲突、为什么降级。

### 6.7 Medical Recheck

医务复测任务和复测记录。用于急症闭环、医学判断、误差原因和关闭校验。

### 6.8 Evidence Chain

围绕事件形成的证据索引，不只是图片或录像路径。

### 6.9 Readiness Check

生产验收前置项检查。它表达依赖是否具备、是否降级、是否人工替代、是否客户阻断。

## 7. 建议主流程

### 7.1 生理采样到事件

1. 生理点位接入并完成标定。
2. worker 从视频帧或上游设备输入形成生理样本。
3. 系统计算 ROI 质量和低可信原因。
4. 系统尝试绑定可信 `person_id`。
5. 无可信身份或低可信时，写入匿名质量窗口或人工复核队列。
6. 满足身份和质量条件时，生成个人生理事件。
7. 事件进入统一事件中心。

### 7.2 行为与生理融合

1. 行为算法生成行为候选或行为事件。
2. 生理 worker 生成生理样本或生理事件。
3. 中枢按同一帧、同一轨迹、同一点位、同一身份或时间窗口执行融合。
4. 融合成功时生成融合关系或融合事件。
5. 融合冲突时保留原事件，标记冲突原因并进入复核。
6. 红色生理急症独立发布，不被普通行为事件覆盖。

### 7.3 急症通道与医务复测

1. 红色生理事件生成医务动作、干警动作和值班领导关注动作。
2. 动作队列检查 readiness。
3. ready 时走真实接口并等待回执。
4. manual_required 时走人工替代闭环。
5. timeout 时升级。
6. 医务人员回填复测记录。
7. 系统检查关闭条件。
8. 事件关闭后，复测结论和误差原因进入治理沉淀。

## 9. 验收切片

### 9.1 V1-P0 第一条主切片

目标：高危点位从生理采样到医务复测闭环可演示。

验收：

- 可配置一个红外/近红外/热成像点位。
- 可产出生理样本和 ROI 质量。
- 可信身份绑定成功时生成个人生理事件。
- 绑定失败时只进入匿名质量统计或复核队列。
- 红色急症进入医务通道。
- 医务可回填复测。
- 事件详情可查看证据链。
- 操作和导出可审计。
- readiness 状态可解释。

### 9.2 V1-P0 第二条主切片

目标：行为事件和生理事件同时出现时不互相吞掉。

验收：

- 同一帧出现倒地和生理急症。
- 行为事件发布。
- 生理急症发布。
- 融合关系可查询。
- 生理急症按红色急症触达医务。

### 9.3 V1-P0 第三条主切片

目标：低可信保护可验证。

验收：

- 遮挡、强运动、热源干扰、厚被或未标定设备导致低可信。
- 不生成个人生理事件。
- 不写入个人基线。
- 写入匿名质量统计或点位整改。
- 低可信原因可审计。

## 12. 建议拆解顺序

### 12.1 需求确认阶段

1. 确认行业口径。
2. 确认事件模型边界。
3. 确认可信身份来源。
4. 确认医务通道验收口径。
5. 确认生理 worker 来源。
6. 确认 V1-P1/P2 的交付深度。

以上六项均已确认。

### 12.2 最小落地阶段

第一阶段只做一个高危点位和一条红色急症闭环：

1. 生理点位台账。
2. 生理样本输入。
3. ROI 质量和低可信保护。
4. 可信身份绑定。
5. 生理事件生成。
6. 医务动作和人工替代闭环。
7. 医务复测回填。
8. 事件详情证据链。
9. readiness 检查。

### 12.3 风险控制阶段

这些能力必须早设计，避免后期返工：

1. `Alert` 与 `Event` 的边界。
2. 生理数据权限。
3. 生理证据脱敏和导出审批。
4. 低可信窗口不能污染个人基线。
5. 人工替代不计入真实接口成功。
6. 心理辅助不单独定性。

## 13. 可信身份来源分析

说明书要求个人生理事件必须绑定可信 `person_id`。当前代码能提供身份线索，但还不能直接证明“可信监管身份”。

### 13.1 当前可用线索

人脸库：

- `FaceLibrary` 表示人脸库。
- `FacePerson` 表示人脸库内归一化人员，包含 `person_name` 和 `person_code`。
- `FaceEntry` 表示人员的人脸条目，包含 `person_id`、`person_name`、`person_code`。
- `FaceMatchRecord` 记录匹配结果，包含 `matched_person_name`、`matched_person_code`、`matched_face_entry_id` 和同帧 `correlation_id`。

同帧关联：

- `Alert.correlation_id` 用于同一帧算法告警、人脸和车牌匹配关联。
- 实时和抓拍算法服务都会生成 `correlation_id`，用于把告警、人脸、车牌结果串起来。

目标追踪：

- `AlgorithmTask` 支持追踪配置。
- `TrackingTarget` 记录任务内 `track_id`。

### 13.2 不能直接等同的概念

`face_person.id` 不能直接等同于说明书里的可信 `person_id`。

原因：

1. 它是人脸库内部归一化人员 ID。
2. 它不一定来自监管业务人员台账。
3. 它不一定具备床位、监区、在押人员编号或业务确认关系。
4. 人脸匹配存在阈值、遮挡、姿态、光照和误匹配风险。
5. 生理事件的合规底线要求“可信身份”，不是“算法猜测身份”。

### 13.3 已确认口径

已确认把身份分成三层：

1. `identity_candidate`：算法候选身份，例如人脸匹配结果、点位/床位绑定线索、轨迹线索。
2. `identity_binding`：业务绑定结果，说明某个样本窗口绑定到哪个监管业务人员。
3. `trusted_person_id`：可用于生成个人生理事件的可信身份。

已确认 V1-P0 规则：

1. 监管系统人员台账或业务确认后的在押人员编号才能作为可信 `person_id`。
2. 人脸匹配只能生成候选身份。
3. 点位/床位绑定只能生成候选身份或弱绑定。
4. `correlation_id` 只能证明同帧关联，不能证明可信身份。
5. 候选身份满足配置阈值并经过业务规则确认后，才能形成 `trusted_person_id`。
6. 无 `trusted_person_id` 时，生理样本只能进入匿名质量统计、点位质量分析或人工复核队列。
7. 个人基线只允许使用可信非告警窗口。

这个结论已作为问题 3 的确认结果，会影响事件生成、基线计算、医务复测和证据链权限。

## 14. 事件模型决策树

这是已确认的事件模型决策记录。

### 14.1 选项 A：把生理事件并入现有 `Alert`

做法：

- 在现有 `alert` 表和告警列表上扩展生理字段、医务字段、状态字段和证据字段。

优点：

- 改动入口少。
- 可以复用现有告警列表、图片、录像和通知链路。
- 短期演示速度快。

问题：

- 现有 `Alert` 语义是算法告警记录，不是业务闭环事件。
- 现有告警支持清空，不适合承载医务复测和审计闭环。
- `task_type` 已被 `realtime` / `snap` 占用，无法表达行为、生理、融合领域。
- 状态、动作、责任链、关闭校验会挤进一个表，后期难以治理。
- 生理证据链会和图片/录像路径混在一起。
- 误报、医务复测、人工替代和 readiness 很难保持清晰边界。

结论：

不推荐作为 V1 主模型。最多让 `Alert` 成为 `Event` 的输入或证据来源。

### 14.2 选项 B：建立统一 `Event` 中心，`Alert` 作为输入

做法：

- 新增统一事件中心，承载行为事件、生理事件、融合事件和人工事件。
- `Alert` 保留为算法告警记录。
- 算法告警、人脸匹配、车牌匹配和生理样本通过 `correlation_id`、`track_id`、点位和时间窗口进入事件中枢。
- 事件中枢负责幂等、去重、分级、TaskFlow、动作、状态机、证据链和关闭校验。

优点：

- 符合说明书中“行为事件、生理事件和人工事件统一承载”的建议。
- 能承载 `created`、`notified`、`in_progress`、`pending_medical_recheck`、`medical_rechecked`、`manual_handled`、`resolved`、`closed` 等状态。
- 能把动作执行状态和 readiness 状态分开。
- 能清晰隔离告警输入、业务事件、证据链、医务复测和治理样本。
- 后续行为闭环、生理闭环和融合闭环都能复用。

问题：

- 需要新增事件主表、状态日志、路由规则、TaskFlow 实例、动作队列和证据链。
- 需要改造前端，从“告警列表”演进到“事件中心”。
- 需要定义从 `Alert` 到 `Event` 的转换规则。

结论：

推荐作为 V1-P0 主模型。

### 14.3 选项 C：行为事件留在 `Alert`，生理事件单独建表

做法：

- 保持现有行为告警在 `Alert`。
- 单独新增 `physiology_event` 和相关表。
- 通过融合表关联两边。

优点：

- 生理闭环不污染现有告警表。
- 比完整事件中心改动少。

问题：

- 行为闭环和生理闭环会形成两套状态机。
- 事件中心、值班台、证据链、关闭校验和审计会重复实现。
- 行为与生理融合时需要跨两套主对象协调。
- 后续人工事件、演练事件、客户阻断事件仍会继续分裂。

结论：

只适合短期过渡，不推荐作为最终模型。

### 14.4 已确认决策

已确认采用选项 B：建立统一 `Event` 中心，`Alert` 作为输入和证据来源。

推荐语义：

- `Alert`：算法侧或设备侧产生的告警记录。
- `Event`：业务侧需要处置、复测、证据、责任链和关闭校验的闭环事件。
- `Event Evidence`：事件引用的证据，可以来自告警图片、录像、规则快照、生理样本、医务复测和操作审计。
- `Fusion Event Link`：行为事件、生理事件和候选身份之间的融合关系。

该方向满足 ADR 条件：难逆转、未来读者会疑惑、且存在真实取舍。已补 ADR，说明为什么不把生理事件直接塞进 `Alert`。

## 15. 医务通道与 readiness 决策树

这是 FR-13、FR-15 和 V1-PHY-007/008/012 的预分析。当前 yFeiEye 已有通知触达底座，但还没有医务闭环。

### 15.1 现有能力

通知渠道：

- 算法任务支持 `alert_notification_config`。
- 告警通知支持 `sms`、`email`、`wxcp`、`http`、`ding`、`feishu` 等方式。
- HTTP/Webhook 渠道可以没有 `notify_users`，通过 `channels` 和模板配置触达外部系统。
- 系统已有短信、邮件、站内信、通知模板和通知日志能力。

这些能力可以作为“动作触达”的基础设施。

### 15.2 缺失能力

当前未发现以下完整领域能力：

1. 医务值班账号和班次。
2. 医务动作队列。
3. 医务系统真实适配器。
4. 医务回执。
5. 医务超时升级。
6. 医务复测任务。
7. 医务复测记录。
8. 医学判断权限隔离。
9. 复测后关闭校验。
10. readiness 状态字典和报表区分。

因此，现有“通知成功”不能等同于“医务闭环完成”。

### 15.3 选项 A：只接真实医务系统

做法：

- V1-P0 必须对接真实医务系统。
- 没有真实接口就不允许验收急症通道。

优点：

- 真实闭环口径最强。
- 报表和回执清晰。

问题：

- 客户现场接口、网络、制度、账号和班次不一定同步具备。
- 容易被外部依赖阻断主链路。
- 与说明书允许人工替代闭环的要求不完全一致。

结论：

不建议作为唯一 V1-P0 路径。

### 15.4 选项 B：只做人工替代闭环

做法：

- 不接医务系统，只记录人工电话、短信、签字和回填。

优点：

- 最快能跑通业务留痕。
- 对客户现场依赖最少。

问题：

- 不能声称真实医务接口成功。
- readiness 报表必须长期标记 `manual_required` 或 `manual_signed`。
- 如果没有动作状态和回执字段，后期接真实适配器会返工。

结论：

可以作为 V1-P0 兜底路径，但不能作为唯一目标状态。

### 15.5 选项 C：真实适配器优先，人工替代兜底

做法：

- 建立统一动作队列和 readiness 检查。
- ready 时走真实医务适配器。
- 未 ready 时走人工替代闭环。
- 两条路径都写入动作执行记录，但状态分开统计。

推荐状态口径：

- `real_success`：真实接口或真实流程返回成功并有回执。
- `manual_completed`：人工替代闭环完成，有留痕。
- `manual_signed`：人工签字确认完成。
- `timeout`：超时未取得回执。
- `skipped_not_ready`：readiness 未具备，动作跳过真实接口。
- `blocked_by_customer`：客户材料、网络、制度或接口人阻断。
- `simulated`：本地联调或演示 profile，生产不得计为成功。

优点：

- 符合说明书“人工替代可闭环，但不得折算真实接口成功”的约束。
- 不被客户接口阻断整体急症闭环。
- 后续接真实医务系统时不重做事件模型。

问题：

- 需要一开始就设计 action 状态、readiness 状态和报表口径。
- 前端要清晰展示“真实成功、人工完成、模拟、客户阻断”的差异。

结论：

推荐作为 V1-P0 方案。

### 15.6 已确认决策

已确认采用选项 C：真实医务适配器优先，人工替代闭环兜底。

已确认语义：

- `Medical Action`：系统为了红色生理急症创建的医务触达动作。
- `Medical Recheck Task`：医务人员需要处理的复测任务。
- `Medical Recheck Record`：医务人员回填的复测结果、医学判断、误差原因和 SOP 执行结果。
- `Readiness Check`：判断真实接口、账号、班次、回执和人工替代配置是否具备。

关键规则：

1. 通知发送成功不等于医务复测完成。
2. 人工签字可以完成业务闭环，但不计入真实接口成功。
3. 模拟适配器只能用于本地联调或演示，不得进入生产成功率。
4. 红色生理急症即使证据链非关键材料暂时失败，也应先触发医务和干警动作，并记录证据缺口。
5. 关闭红色生理事件前必须检查医务复测、动作状态、处置记录、证据链和责任链。

## 16. 项目模块落地边界

以下拆分用于把需求落到 yFeiEye 当前工程结构，避免把所有能力都堆进单个服务。

### 16.1 WEB

承载范围：

- 事件中心、事件详情、值班处置、证据链查看。
- 生理点位配置、ROI 质量、生理指标时序、生理事件详情。
- 医务复测台、复测回填、医学判断入口和权限隔离。
- readiness 页面、动作队列、人工替代记录。
- 数据治理、难例池、模型治理和演练页面。

需要注意：

- 现有告警列表可以继续展示 `Alert`，但不能替代事件中心。
- 生理证据、医务判断和心理辅助必须做权限隔离。
- 前端报表必须区分事件状态、动作状态、readiness 状态和统计状态。

### 16.2 VIDEO

承载范围：

- 摄像头、NVR、ONVIF、GB28181、流转发、录像回放等视频能力。
- 算法任务、实时/抓拍任务、检测区域、告警生成。
- 生理 worker 的接入或调度入口。
- 生理样本、ROI 质量、匿名质量窗口的采集侧写入。
- `Alert` 到 `Event` 的输入桥接。

需要注意：

- `Alert` 保留为算法告警记录。
- `correlation_id`、`track_id`、点位和时间窗口可作为事件融合线索。
- 生理 worker 如果在 VIDEO 内实现，要避免把医务闭环和业务事件状态机塞进算法服务。

### 16.3 DEVICE / iot-sink

承载范围：

- Kafka 告警消费、告警落库、MinIO 图片回写。
- 通知消息转发。
- 未来可承载事件中枢、动作队列、readiness 和证据链的 Java 侧实现。

需要注意：

- 现有 `iot-sink` 的告警处理更偏消息落库和通知，不是完整 TaskFlow。
- 如果事件中枢放在 Java 侧，需要明确与 VIDEO 的数据库边界和消息契约。
- 动作执行、人工替代、超时升级和回执必须有独立状态，不应混入告警通知字段。

### 16.4 DEVICE / iot-system

承载范围：

- 用户、角色、菜单、权限。
- 操作日志、登录日志。
- 短信、邮件、站内信、通知模板。
- 医务权限、审计员权限、readiness 管理权限的菜单和按钮授权。

需要注意：

- `events:medical_recheck`、`medical:recheck`、`physiology:evidence:view` 等权限应接入现有菜单权限体系。
- 医务判断、导出、删除、规则修改和权限分配必须进入操作审计。

### 16.5 AI

承载范围：

- 模型训练、模型导出、模型服务和版本管理。
- 生理模型治理的基础能力可复用模型版本、部署和评估机制。
- V1-P1 的影子模式、灰度、冠军-挑战者和专家评审可以基于现有模型管理扩展。

需要注意：

- 生理模型不能直接上线到生产主通道，必须经过 readiness、评审和回滚策略。
- 灰度和影子模式不得影响红色急症主通道安全。

### 16.6 TASK

承载范围：

- C++ 边缘推理、RTMP 推流、报警回调和高性能多路处理。
- 可作为行为识别和部分边缘生理采样的执行节点。

需要注意：

- TASK 更适合做边缘推理和回调，不适合承载医务复测、证据链和事件关闭校验。
- 若生理 worker 下沉到 TASK，仍需把样本、质量、事件和动作状态回写到中心侧。

### 16.7 数据层

建议新增数据域：

- 事件中枢：`event_main`、`event_status_log`、`event_dedup_log`、`event_route_rule`。
- TaskFlow：`taskflow_definition`、`taskflow_instance`。
- 动作处置：`action_queue`、`action_execution_log`、`manual_action_record`、`event_close_check`。
- 证据链：`event_evidence`、`evidence_file`、`recording_mark`、`export_request`、`export_audit`。
- 生理监测：`physiology_sample`、`physiology_quality_window`、`physiology_baseline`、`physiology_event_detail`。
- 医务复测：`medical_recheck_task`、`medical_recheck_record`。
- 融合关系：`fusion_event_link`。
- readiness：`adapter_config`、`readiness_check`。
- 治理：`physiology_governance_sample`、`failure_mode`、`hard_case_pool`、`waveform_annotation`。

需要注意：

- 已有数据库必须通过 migration 升级，不能只支持初始化新库。
- 生理样本、医务复测、心理辅助和导出材料都属于敏感数据。
- 个人基线只能由可信非告警窗口生成。

### 16.8 第一阶段工程落点建议

建议第一阶段只选一条高危点位红色急症链路：

1. VIDEO 产出生理样本或接入上游生理样本。
2. 中心侧完成可信身份绑定和低可信保护。
3. 中心侧生成 `Event`。
4. 动作队列触发医务动作、干警动作和值班领导关注动作。
5. readiness 不具备真实接口时走人工替代闭环。
6. WEB 提供事件详情、证据链和医务复测回填。
7. 关闭前执行复测、动作、证据和责任链校验。

### 17.4 不通过条件

出现以下任一情况，草案判定为不满足说明书 V1：

1. 无可信 `person_id` 仍生成个人生理事件。
2. 低置信、遮挡、ROI 丢失或未标定数据写入个人基线。
3. 红色生理急症被普通行为事件覆盖、降级或延迟到非急症队列。
4. 通知发送成功被当作医务复测完成。
5. 人工替代、模拟适配器或客户阻断被统计为真实接口成功。
6. 生产上线没有 readiness 探针、迁移脚本和失败模式记录。

### 20.4 已确认：事件模型边界

生理事件是否并入现有 `Alert`，还是建立统一 `Event` 中心并让 `Alert` 作为输入和证据来源？

确认结论：建立统一 `Event` 中心，`Alert` 作为输入和证据来源。

原因：当前代码里的 `Alert` 具备告警、图片、录像、通知和同帧 `correlation_id` 能力，但缺少说明书要求的事件状态机、动作队列、责任链、医务复测、证据链、关闭校验和 readiness 口径。把生理闭环直接塞进 `Alert` 会把告警记录、处置事件和医务闭环混成一个概念。

### 20.5 已确认：可信 `person_id` 来源

可信 `person_id` 来自哪里：人脸、床位/点位绑定、监管系统人员台账，还是人工确认？

确认结论：以监管系统人员台账或业务确认后的在押人员编号作为可信 `person_id`；人脸、床位/点位绑定和 `correlation_id` 只能作为身份候选证据，不能单独生成个人生理事件。

原因：说明书要求“无可信 `person_id` 不生成个人生理事件”。当前代码的人脸库、人员库和 `FaceMatchRecord` 可以提供姓名、编号、相似度、阈值和同帧关联，但它们仍是匹配候选，不等同于监管业务身份。

### 20.6 已确认：医务通道验收口径

医务通道 V1-P0 是否必须接真实医务系统，还是允许人工替代闭环先验收？

确认结论：真实医务适配器优先，人工替代闭环兜底。生产验收必须区分 `real_success`、`manual_completed`、`manual_signed`、`simulated`、`blocked_by_customer` 和 `skipped_not_ready`，人工替代可以证明业务处理完成，但不能统计为真实接口成功。

原因：说明书要求医务急症通道和医务复测属于 V1-P0，同时明确模拟、人工签字、客户阻断不得折算为真实接口成功。只接真实接口容易被客户现场条件阻断；只做人工替代又会弱化生产 readiness 和真实闭环能力。

### 20.7 已确认：生理 worker 来源

生理 worker 由 yFeiEye 自研，还是对接上游红外/热成像设备输出？

确认结论：V1-P0 以对接上游红外/近红外/热成像设备或厂商 SDK 输出为优先，自研 worker 作为兜底、并行能力或后续替换路线；yFeiEye 定义统一 `Physiology Sample` 输入契约、质量标签、模型版本和 readiness 校验，不让自研 worker 阻塞第一条红色急症闭环。

原因：说明书验收重点是“可信身份 - 生理样本 - 生理事件 - 医务复测 - 证据链 - readiness”的业务闭环，不是必须先自研完整生理算法。项目当前已经有视频、算法任务、告警和模型底座，但没有成熟的红外/近红外生理 worker；先统一接入契约能降低 V1-P0 风险，同时保留自研扩展空间。

### 20.8 已确认：V1-P1/P2 交付深度

V1-P1/P2 能否先只做数据结构和入口预留，还是必须完整上线？

确认结论：V1-P1 必须至少做最小可用的数据治理和模型治理入口，V1-P2 可以先做数据结构、权限、审计和入口预留，不阻塞 V1-P0 红色急症闭环。心理辅助合规标识 `not_standalone_determination` 必须从 V1-P0 阶段保留。

原因：说明书把生理数据治理、模型治理、红队演练、失败模式库纳入 V1 范围，但 V1-P0 的生命安全闭环优先。若 P1/P2 完全不留入口，后续医务复测回流、误差原因、难例池、模型灰度和心理辅助合规会返工；若 P1/P2 全量上线，又会拖慢第一条急症闭环。
