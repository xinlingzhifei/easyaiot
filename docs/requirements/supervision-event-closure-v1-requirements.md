# 司法监管事件处置闭环 V1 需求说明

状态：草案
目标项目：yFeiEye
上游依据：现有 yFeiEye 设备、视频、算法、告警、通知、证据、权限和审计能力；`docs/requirements/iv-physiology-v1-requirements-draft.md`；`docs/prd/iv-prison-physiology-v1-prd.md`

## 1. 背景

yFeiEye 当前已经具备设备接入、视频流、算法任务、告警生成、告警通知、图片/录像证据、地图分布、人脸库、车牌库、权限和操作日志等底座能力。现有能力已经可以回答“哪里出现了异常”，但还不能完整回答司法监管业务最关心的后续问题：

1. 这个异常是否形成监管事件？
2. 谁负责接收、到场、处置和复核？
3. 处置是否有证据和责任链？
4. 事件为什么可以关闭？
5. 事后督察、复盘和追责时能否还原全过程？

因此，下一阶段的产品主线应从“告警管理”升级为“监管事件处置闭环”。

## 2. 一句话边界

`Alert` 是算法或设备告警输入，负责发现异常；`Supervision Event` 是监管事件，负责承载状态、责任、动作、复核、关闭和证据链；`Disposal Task` 是事件处置任务，负责把事件落实到岗位、人员和操作。

这不是给告警列表增加几个处理字段，也不是替换现有告警能力，而是在现有告警、视频、通知、证据和权限能力之上建立司法监管业务闭环。

## 3. 适用场景

V1 覆盖监狱、看守所、司法行政戒毒所中可共用的监管事件闭环能力。场所差异通过事件类型、SOP、关闭规则和权限规则配置表达。

优先覆盖以下事件大类：

1. 生命健康：倒地、突发疾病、生理红色急症、自伤自残风险。
2. 监管秩序：打架斗殴、聚集冲突、异常接触、长时间静止、离岗、滞留。
3. 区域安全：越界、重点区域入侵、周界异常、门禁异常。
4. 戒毒专项：戒断异常、康复训练异常、心理/行为异常、违禁品风险。
5. 设备保障：摄像头离线、视频中断、重点区域设备不可用。

## 4. 现有能力复用

可以复用：

- 告警输入：`VIDEO.models.Alert`、iot-message `AlertDO`、Kafka 告警通知链路。
- 证据素材：告警图片、MinIO 图片下载地址、录像路径、录像回放入口、抓拍空间和录像空间。
- 位置和设备：摄像头、设备目录、地图坐标、GB28181/ONVIF/NVR 接入。
- 身份线索：人脸库、车牌库、`correlation_id`、任务和设备上下文。
- 系统底座：用户、角色、部门、菜单权限、通知渠道、操作日志。

不能直接复用为完成态：

- `Alert` 不能承担事件生命周期、责任链、复核、关闭校验和督察复盘。
- 图片路径和录像路径只是证据素材，不等于完整证据链。
- 通知成功不等于处置完成、医务复核完成或事件可以关闭。
- 技术管理员权限不等于业务处置、复核和关闭权限。

## 5. 核心对象

### 5.1 Alert

算法、设备或人工上报产生的异常线索。它可以成为监管事件的输入或证据来源，但不承担关闭语义。

### 5.2 Supervision Event

监管事件。用于承载事件类型、等级、状态、责任链、处置任务、复核记录、关闭校验、证据链和审计记录。

### 5.3 Disposal Task

处置任务。用于把事件派发给具体责任单位、岗位和人员，记录接收、到场、处置、补充、复核、关闭等过程。

### 5.4 Action

事件下的责任动作，例如现场到场、医务复核、康复复核、领导关注、运维恢复、催办升级。

### 5.5 Evidence Chain

围绕事件形成的可复盘证据包，包含原始告警、图片、录像、设备、点位、人员、时间线、处置记录、复核记录、关闭记录和操作日志。

### 5.6 Rule Tables

三类主规则表是 V1 的规则内核：

1. 告警转监管事件规则表。
2. 关闭校验规则表。
3. 职责隔离与数据权限表。

四类子规则表用于支撑落地：

1. 升级因子表。
2. 证据模板表。
3. 任务时限表。
4. 告警合并表。

## 6. 主流程

1. 系统接收算法、设备或人工上报告警。
2. 告警根据“告警转监管事件规则表”判断是否生成监管事件。
3. 系统为事件计算默认等级，并根据重点人员、重点区域、夜间、多人、伤情、重复和超时等升级因子调整等级。
4. 事件生成处置任务和责任动作。
5. 指挥中心或责任单位派发任务。
6. 责任人接收任务并记录到场、核实和处置结果。
7. 高等级或敏感事件进入医务、康复心理、领导或督察复核。
8. 系统按关闭校验规则检查责任链、证据链、复核记录、关闭权限和例外审批。
9. 校验通过后事件关闭归档；校验不通过时进入退回补充、无法确认审批或转重大事件。
10. 关闭后可进行督察复盘、导出审批和统计分析。

## 7. 事件状态

V1 建议事件状态为：

1. `alert_received`：告警已接收。
2. `event_candidate`：候选监管事件，等待规则或人工确认。
3. `created`：监管事件已创建。
4. `dispatched`：处置任务已派发。
5. `accepted`：责任人已接收。
6. `handling`：现场处置中。
7. `pending_recheck`：等待复核。
8. `rework_required`：退回补充。
9. `pending_close_check`：等待关闭校验。
10. `exception_review`：无法确认或无法复核的例外审批。
11. `closed`：已关闭归档。
12. `transferred_major`：已转重大事件。

## 8. 事件等级

| 等级 | 含义 | 典型事件 | 关闭要求 |
| --- | --- | --- | --- |
| L1 一般事件 | 低风险，可快速处理 | 普通设备离线、普通误报、普通滞留 | 处理说明、结果分类、操作日志 |
| L2 重要事件 | 影响监管秩序或需要现场确认 | 越界、聚集、重点区域滞留 | 责任人、到场记录、现场结果、证据 |
| L3 重大事件 | 涉多人、重点人员、伤情、冲突或严重秩序风险 | 打架、自伤风险、违禁品风险 | 复核意见、领导确认、完整证据链 |
| L4 生命安全事件 | 涉生命健康、突发疾病、生理红色急症或严重戒断异常 | 倒地、突发疾病、生理红色急症 | 医务/康复复核、领导关闭、无法复核审批 |

等级可以被规则升级，不能被普通处理人手动降级。降级必须留痕并经过有权限角色确认。

## 9. 关闭结果

关闭结果必须使用受控字典：

1. `true_abnormal_handled`：真实异常已处置。
2. `false_alarm_confirmed`：误报已确认。
3. `duplicate_merged`：重复告警已合并。
4. `device_cause_transferred`：设备原因已转运维。
5. `unable_to_confirm_approved`：无法确认已审批。
6. `transferred_major_event`：已转重大事件。

误报不能删除原始告警和证据。无法确认不能作为普通关闭捷径；L3/L4 的无法确认必须走领导审批。

## 10. 权限和敏感数据边界

- 指挥中心有调度权，但不能替代现场处置和医务结论。
- 现场民警负责现场事实和处置过程，但不能直接关闭 L3/L4。
- 医务人员负责医疗复核和体征/伤情结论，不能修改原始告警和现场记录。
- 康复/心理人员负责戒毒专项、康复和心理复核，相关结论为辅助性质，不能单独作为惩戒或最终监管定性。
- 值班领导负责重大事件确认、无法确认审批和 L3/L4 关闭。
- 督察/审计人员负责事后复盘，不能修改处置过程。
- 系统管理员负责配置菜单、字典、规则和权限，不能伪造业务处置、复核和关闭记录。

## 11. P0 范围

V1-P0 只交付可运行、可解释、可审计的监管事件处置闭环：

1. 告警转监管事件规则。
2. 监管事件模型。
3. 处置任务闭环。
4. 责任动作和时间线。
5. 证据链基础索引。
6. 关闭校验规则。
7. 角色职责隔离。
8. 最小验收脚本。

## 12. P1/P2 范围

P1：

- 超时升级、催办、合并去重。
- 生理红色急症接入。
- 戒毒康复异常专项接入。
- P0 统计口径。

P2：

- 治理样本、模型优化、趋势报表、督察复盘、导出审批、跨场所差异化配置。

## 13. 验收脚本

P0 至少通过以下脚本：

1. 普通告警闭环：告警 -> 监管事件 -> 派发 -> 接收 -> 处置 -> 关闭。
2. 生命安全事件闭环：倒地/突发疾病 -> 现场到场 -> 医务复核 -> 领导关闭。
3. 戒毒异常闭环：戒断/康复异常 -> 大队处理 -> 医务或康复复核 -> 关闭。
4. 驳回补充：证据或说明不足 -> 复核驳回 -> 补充 -> 再复核 -> 关闭。
5. 超时升级：责任人未接收或未处理 -> 催办 -> 升级 -> 留痕。
6. 误报归档：误报确认后保留原始告警、误报原因和确认人。
7. 关闭拦截：缺责任人、缺处置记录、缺复核或缺领导确认时不能关闭。
8. 权限隔离：技术管理员不能伪造业务闭环；普通处理人不能关闭 L3/L4。
